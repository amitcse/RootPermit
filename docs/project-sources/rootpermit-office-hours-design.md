## Problem Statement

Agent builders increasingly run autonomous or semi-autonomous agents on cloud VMs, local Linux computers, Raspberry Pis, and home servers. Those agents occasionally need to change privileged host state, such as installing a package. Today the operator must either supervise the command directly, give the agent broad `sudo` authority, or bolt together a remote command-approval mechanism.

RootPermit should let an untrusted agent request one typed state transition without receiving a root identity, shell, reusable credential, or time-bounded privileged session. A trusted local broker resolves the request into an immutable artifact/version/action set, enforces root-owned policy, obtains a human signature over that set, prevents silent re-resolution, and returns a structured result.

The first release is an open-source/research project. Its job is to prove that this trust chain works end to end and is useful enough that an agent builder installs it on a real machine.

## What Makes This Cool

The complete demonstration is one coherent story:

1. A developer installs the open-source RootPermit edge components and enrolls the machine with the free official RootPermit control plane.
2. They add `rootpermit` to an existing agent with minimal integration.
3. The unprivileged agent requests `package.install("ffmpeg")` on an Ubuntu VM.
4. The local broker resolves and freezes the package artifacts, versions, and predicted actions.
5. The hosted approval website shows the packages, versions, dependencies, removals, repositories, download size, disk impact, target device, and expiry from the broker-signed request.
6. The developer confirms the exact broker-signed request with a passkey on the trusted hosted approval website, without reaching the machine console.
7. The broker executes the approved artifact/version/action set without silent re-resolution and returns a structured result to the agent.
8. The developer can inspect a broker-signed receipt showing what was requested, approved, and executed.
9. The same flow runs on a Raspberry Pi OS ARM64 machine without a second implementation.

The approval gesture is the narrative climax. Easy integration, typed semantics, local policy, passkey-bound approval, and verifiable receipts make it credible. The official hosted service removes control-plane setup from the first-run experience.

## Target User and Reference Environments

### Primary user

An agent builder or developer who already lets an agent perform meaningful work on a Linux host, but refuses to grant that agent unrestricted `sudo`.

### Canonical demonstration

- Ubuntu Server 26.04 LTS, AMD64 cloud image, pinned by published image identifier and digest in the test fixture.
- Generic unprivileged agent or shell-based test harness using `rootpermit`.
- `package.install` as the only privileged operation in the first vertical slice.

### Portability proof

- Raspberry Pi OS Lite 64-bit based on Debian 13 (Trixie), 2026-06-18 release, ARM64.
- Reference hardware: Raspberry Pi 5 Model B, 4 GB, with a recorded bootloader/firmware baseline and no non-default APT hooks. Before the portability gate begins, the fixture must replace the human-readable release label with the exact official image URL/identifier, published SHA-256, flashed-image digest, kernel/firmware versions, and package-manager baseline used by CI.
- The same protocol, broker, relay, web approval flow, and operation behavior.
- Platform-specific packaging is allowed; a separate product path is not.

## Constraints

- No arbitrary command path, advanced escape hatch, privileged shell, or reusable elevated identity.
- The agent, its account, its descriptions, agent-controlled files, network, and notification provider may be malicious or compromised.
- Root-owned broker code, operation helper, policy, kernel, repository-signature system, enrolled broker key, the official hosted control plane, its approval web application and deployment pipeline, and the user's passkey authenticator are trusted for the MVP.
- The exact repository package artifacts selected by an approved hash are authorized to run root maintainer code. Repository signatures prove origin and byte integrity, not safety; RootPermit does not audit or sandbox package behavior.
- The hosted service must not possess a root credential, broker signing key, passkey private key, or direct execution channel. A service compromise can deny service, expose retained metadata, attack tenant isolation, or deceive a user about what is being approved. It still must not be able to make the broker accept an approval without a valid per-request passkey assertion for a locally created, unexpired request.
- The first milestone must be security-complete for one operation before adding operation breadth.
- Routine MVP approval is phone-only through the trusted official hosted approval UI. The protocol does not expose an MVP `dual` assurance mode, local-confirmation substate, or local escalation path.
- Ubuntu AMD64 is the reproducible first-run path and security-complete hosted-alpha gate. Raspberry Pi OS ARM64 is the portability gate for the public MVP release.
- The free official control plane is the only supported coordination and approval service. Its source is public under Apache-2.0, but RootPermit provides no self-hosting package, deployment guide, compatibility commitment, migration guarantee, or support for third-party deployments.
- Initial enrollment requires an authenticated root-controlled administrative session, which may be a local console, serial console, or SSH session. Physical presence is not required. A hosted login, browser-only action, or QR copied through agent-controlled output is not trusted enrollment and cannot substitute for confirmation through that root-controlled session.
- Package installation is artifact/action-set exact only in a narrow sense: RootPermit freezes the package artifacts supplied to APT/dpkg and the solver actions it initiates, and forbids silent re-resolution. It does not constrain or predict arbitrary network access, subprocesses, package-state changes, or other host mutations performed by approved root maintainer scripts and triggers against live host state.

## Premises

1. Remote phone approval is useful but is not the unique product claim.
2. Typed, broker-resolved state transitions are the wedge.
3. RootPermit complements agent sandboxes and conventional access management; it does not replace them.
4. Arbitrary shell strings are permanently outside the RootPermit authorization boundary.
5. The official control plane and approval website are trusted components in the MVP. RootPermit must state this directly and must not claim that a control-plane compromise cannot substitute the transaction shown to the approver.
6. The first demo must visibly prove the semantic difference by showing a resolved `apt` transaction, not only `apt install ffmpeg`.
7. One security-complete operation is more informative than a generic operation platform whose trust chain has not been exercised.
8. Public source is an auditability property, not a self-hosting promise and not proof that the deployed service matches the published source.

## Why the MVP Uses Web Approval

The MVP deliberately trusts the RootPermit-operated control plane, approval website, domain, and deployment pipeline. That makes a web approver a reasonable scope tradeoff while the project proves its primary proposition: a compromised agent can request only typed, locally constrained operations and never receives a privileged identity or credential.

This tradeoff does not erase the transaction-substitution threat. With ordinary WebAuthn, malicious same-origin JavaScript can display benign operation A while passing operation B's digest as the challenge. The authenticator proves user verification and binds its assertion to the relying-party origin and challenge, but it does not independently render RootPermit's operation details. The broker can receive a cryptographically valid assertion for B even though the human believed they approved A.

The MVP therefore uses one approval mode: the trusted web application verifies the broker envelope, reconstructs the canonical digest, renders structured fields, and requests a passkey assertion over that digest. This protects against the agent, network, notification provider, and ordinary cross-tenant message substitution, but not a compromised official web deployment. That limitation is explicit and accepted under the MVP trust model.

High-assurance dual confirmation is a possible post-MVP defense-in-depth feature for deployments that are willing to require a second trusted local or organizational confirmation. It is not implemented, negotiated, tested, documented as available, or represented in MVP protocol fields or state transitions.

A future independently distributed native app, browser extension, or desktop signer may remove the hosted page from the transaction-rendering trust boundary. Browser-native transaction-confirmation APIs may offer another path, but ordinary WebAuthn alone does not provide a generic trusted display for RootPermit operations.

## Approaches Considered

### Approach A: Security-complete `package.install` vertical slice

Build the whole trust chain for one operation: `rootpermit`, root broker, frozen artifact/version/action set, hosted control plane, dedicated approval website, passkey-bound decision, constrained execution, structured result, and signed receipt.

- Effort: Medium for the protocol/security prototype, approximately 6–10 small-team weeks or 2–4 AI-assisted builder weeks. The hosted alpha and public release are separate projects with separate estimates in the milestone gates; the full public-service bar is not a 7–12 week deliverable.
- Risk: Medium. The product surface is narrow, but transaction freezing, enrollment, and key lifecycle require careful design.
- Reuses: The PRD's typed-operation protocol, local-policy model, relay split, request digest, and receipt model.
- Strength: Proves the actual security thesis and produces the canonical demo early.
- Cost: Operation abstractions may require refinement when the second operation is added.

### Approach B: Typed-operation platform from day one

Design the generic operation framework first and ship packages, service control, managed services, managed files, policy administration, full receipts, multiple Linux distributions, and a production hosted service together.

- Effort: Extra large. A non-production multi-operation prototype may take approximately 4–6 human-team months or 8–12 AI-assisted weeks. Meeting the same hosted production, two-platform, supply-chain, and external-review bar as Approach A would exceed its 9–15 human-team month / 5–9 AI-assisted month public-release estimate.
- Risk: High. A broad security boundary and many cross-operation interactions must be reviewed before real usage validates the model.
- Reuses: Most of the existing PRD's full MVP scope.
- Strength: The first public release looks like the intended platform.
- Cost: Delays proof of the trust chain and encourages premature abstractions.

### Approach C: Local-first protocol prototype

Build the broker and a separate reference signer around a local or disposable opaque mailbox, while deferring the production hosted service, accounts, polished enrollment, notifications, and multi-device history.

- Effort: Small to medium. Approximately 4–7 human-team weeks or 2–3 AI-assisted weeks.
- Risk: Medium. Cryptographic inspection is easy, but onboarding friction may hide whether agent builders value the complete product.
- Reuses: Broker, request envelope, signature, and receipt concepts.
- Strength: Makes the cryptographic protocol easy for researchers to inspect.
- Cost: Proves the protocol more strongly than the intended user experience.

## Recommended Approach

Proceed with Approach A. It keeps the entire intended product loop while limiting the first security review to one typed operation. The production hosted control plane is part of that product loop, not a later compatibility demonstration. Approach C remains useful only as a protocol test harness.

The approved interaction model has three states:

1. Inspect the broker-resolved transaction in the trusted hosted approval UI.
2. Confirm the request digest with a passkey.
3. Verify the execution receipt.

Wireframe: `rootpermit-approval-wireframe.html`.

## System Boundaries

| Component | Privilege/trust | MVP responsibility |
| --- | --- | --- |
| Agent | Untrusted, unprivileged | Submit typed `package.install` request; receive structured status/result |
| `rootpermit` | Unprivileged client | Validate basic input shape; communicate over the local broker API |
| `rootpermitd` | Root, trusted | Enforce policy, resolve/freeze artifact and action set, sign envelope, verify approval, prevent silent re-resolution, sign receipt |
| Package helper | Root, narrowly trusted | Interact with `apt`/`dpkg` without accepting shell syntax |
| `rootpermit-relay` | Unprivileged edge component | Transport broker-signed envelopes and WebAuthn assertions; poll/retry; hold no root credential or approval key |
| Official control plane | Trusted hosted service, but not a root principal or lifecycle authority | User/device accounts, tenant isolation, immutable signed-envelope and decision mailbox, broker-signed lifecycle-event storage, derived UI projection, notification, rate limits, web-session security, credential quarantine, and audit metadata |
| Approval website | Trusted transaction renderer | Verify broker envelope, canonicalize and render structured fields, construct the canonical decision object and use its SHA-256 hash as the WebAuthn challenge, obtain a passkey assertion, and display receipts |
| Passkey authenticator | Trusted approval key holder | Retain one of at most five explicitly broker-pinned credentials per device, keep each credential independently identifiable and revocable, and require user verification for every approval assertion |
| Repository system and approved package code | Trusted/authorized within stated limits | Authenticate metadata and bytes; execute the explicitly approved artifact hashes. RootPermit does not establish that package behavior is safe |

## Enrollment

Enrollment must bind the local broker, hosted user account, device record, and passkey credential without allowing an agent to enroll itself as an approver.

1. The user creates an account on the official service using OIDC or an email sign-in mechanism. Account authentication is separate from the approval passkey registered on the dedicated approval origin. Recovery of the hosted account cannot create or restore approval authority.
2. An administrator invokes the enrollment command from an authenticated root-controlled administrative session. The session may be a directly attached or serial console, or an SSH session whose authentication and host-verification controls are trusted by the administrator; physical presence is unnecessary. `rootpermitd` generates its device signing key locally and renders a one-time URL/QR and a comparison code to that session. The payload contains the official endpoint, device identifier, broker public key, short-lived single-use pairing nonce, protocol version, and approver generation.
3. The authenticated website opens the pairing payload and shows the same code. The user confirms the match both in the web session and through the original root-controlled administrator session. Merely possessing the pairing payload, controlling the hosted account, or printing the same payload through an agent-controlled process cannot supply the broker-side confirmation.
4. The control plane stores the broker public key and the proposed complete eligible passkey credential set as `provisional`. The set contains one to five distinct credential IDs/public keys plus their credential-class metadata. It cannot deliver approvable requests for that device yet. A dedicated official enrollment key, pinned in the installed broker package, signs a canonical enrollment statement containing the account ID, device ID, broker public key, exact proposed credential set, nonce, expected RP ID/origin, protocol version, and next approver generation. A set containing zero credentials, duplicates, more than five active credentials, an unrecognized credential state, or a hosted-only addition not initiated by the root-controlled broker is rejected.
5. For initial enrollment and every credential-set update, the web client obtains a user-verified passkey assertion from one credential in the proposed new set over the digest of that complete enrollment statement. Adding or replacing a credential on an active device requires the currently active broker and the root-controlled administrative confirmation, but never an assertion or consent from an already pinned credential. This remains true when every old credential is lost or unavailable. A proposed credential's assertion proves possession but cannot authorize its own addition by itself: the broker accepts the complete set only from the official-service-signed statement after verifying the root-authorized transcript, then atomically pins that exact set locally.
6. The broker verifies the official service signature, pinned service key generation, passkey assertion, origin/RP ID, nonce, code confirmation, and complete transcript before atomically marking the enrollment `active`. For a credential-set update, the same transaction advances the approver generation and moves every non-executing request bound to an older generation from `planning`, `pending`, or `approved` to terminal `stale`; no request or consumed approval is migrated. A request already in `executing` continues under its original generation. If the device was `approval_locked`, successfully pinning a non-empty replacement set atomically returns it to `active` without changing its broker identity or historical records. The control plane marks the enrollment active only after receiving the broker-signed activation acknowledgement and applies the broker's signed lifecycle events to its request projections.
7. A mismatch, timeout, restart without durable provisional state, duplicate nonce, origin/RP-ID mismatch, or missing acknowledgement moves enrollment to `failed`; the nonce can never be reused. Re-enrollment or approver replacement requires an explicit root-controlled local action.

The WebAuthn verification and pairing construction must use reviewed libraries. Inventing a custom pairing cryptosystem is out of scope. The normative enrollment paths are `unpaired → provisional → active`, `provisional → failed | expired`, `active → approval_locked` when the final credential is revoked, `approval_locked → provisional → active` for root-controlled credential recovery, and `active | approval_locked → unpaired` after a successful root-controlled unenrollment. A failed recovery returns to `approval_locked`, not `unpaired`; failed or blocked unenrollment leaves the prior state unchanged; no request approval is accepted outside `active`. Canonical encoding, signature algorithms, domain-separation labels, credential identifiers, official enrollment-key rotation, RP ID/origin checks, downgrade handling, signed messages, crash recovery, retry/idempotency rules, and pairing transitions must be normative in a reviewed protocol specification before broker or web authorization code is implemented.

Hosted account recovery may restore access to the website and may initiate credential revocation, but it cannot add, replace, restore, or reactivate a broker-authorized passkey, directly increment broker-owned generations, change a device binding, or remotely cancel a request in the MVP. Any approval-credential addition or replacement requires a fresh root-controlled local enrollment. Reaching the five-active-credential cap requires root to revoke or remove an existing credential before another can become active; the broker never evicts one implicitly.

Unenrollment is a separate destructive lifecycle operation, not a synonym for credential revocation, hosted deletion, or `approval_locked`. Only an authenticated root-controlled console or trusted SSH command may initiate and confirm it. The broker rejects unenrollment while a request is `executing` or package state is `recovery_required`; otherwise it atomically invalidates non-executing requests, revokes the pinned credential set, emits the signed final binding event, retains historical verification material, and becomes `unpaired`. The hosted service removes the active binding only after verifying that broker acknowledgement. A later connection requires the complete fresh enrollment ceremony.

## Package Operation Contract

The first operation accepts exactly one native-architecture binary package name. The agent cannot provide a version, architecture, repository, URL, local path, APT option, environment variable, or command fragment.

- Package names must match Debian's valid binary-package-name grammar and a root-owned allow/deny policy.
- Virtual packages, local `.deb` files, source packages, foreign architectures, explicit downgrades, package removals, and held packages are rejected in the first slice.
- If the requested package is already installed at the resolved version, the broker returns a signed `no_change` terminal event.
- An upgrade of the requested package or dependencies is allowed only when root-owned policy permits it and the full version transition is prominent in the approval UI.
- Any plan containing removals or downgrades is rejected rather than merely labeled high risk.
- Recommends behavior, conffile behavior, noninteractive mode, locale, proxy use, and all APT options are fixed by root-owned broker policy and recorded in the request.
- Planning requires authenticated repository metadata that satisfies configured `Valid-Until`, signing-key validity/revocation, maximum metadata age, and root-owned mirror policy. Stale or replayed metadata is rejected before approval. After approval, later repository publication or signing-key expiry does not invalidate an intact frozen snapshot and cached artifacts unless root-owned policy explicitly revokes that repository/key and therefore makes the request stale.
- Package names, versions, repository labels, maintainer metadata, and descriptions are untrusted display strings. The approval UI escapes them, prevents bidi/control-character spoofing, and never lets them resemble trusted device or policy labels.

The approval screen separates the directly requested package from dependencies, makes upgrades prominent, and warns that maintainer scripts, triggers, service starts, and other package side effects cannot be fully predicted from metadata.

## Request and Approval Flow

1. The agent calls `rootpermit package install ffmpeg` as an unprivileged user in the allowlisted request group.
2. `rootpermitd` authenticates the local peer from kernel-provided Unix-socket credentials and persists the peer's effective UID as `requester_uid` with the intake and request. Root-owned policy decides whether that UID may submit the typed operation. PID, executable, cgroup/systemd unit, and agent-supplied labels are separately captured where available for policy and audit, but they cannot define or narrow cancellation authority. The broker validates the typed input and rejects unsupported repositories, flags, or package sources.
3. The package helper verifies the configured repository chain from `InRelease` or `Release` plus `Release.gpg` through referenced `Packages` indexes to each artifact hash. It snapshots the authenticated metadata, source configuration, pin preferences, and selected artifacts in root-owned content-addressed storage.
4. The broker resolves the dependency graph using a pinned APT configuration and records exact package names, architectures, epochs/versions, artifact hashes, repository origins, metadata hashes and freshness evidence, dependencies, upgrades, download size, disk delta, policy digest, approver generation, and package-manager pre-state. It also records an authoritative monotonic lifetime and boot identifier plus informational signed wall-clock `created_at`/`expires_at` values.
5. The broker canonicalizes this envelope, computes its digest, signs it with the enrolled broker key, and persists the pending request before exposing it to the relay.
6. The relay/control plane transports the signed envelope. Notification payloads carry only an opaque request identifier.
7. The approval website fetches the envelope, verifies the broker signature against the enrolled device record, validates canonical encoding plus the informational timestamp shape/plausibility, recomputes the digest, and renders verified structured fields with an approximate countdown. Only the broker enforces the authoritative monotonic expiry; stronger remote freshness would require a fresh broker-signed status response. Agent-supplied rationale appears in a separately labeled untrusted section. The service and page are trusted to perform these steps honestly in the MVP.
8. The browser builds a canonical decision object containing the domain-separation label, decision bit, request digest, request ID, device ID, authoritative lifetime identifier, approver generation, and protocol version. The WebAuthn challenge is exactly `SHA-256(canonical_decision_object)`. Fields already inside the broker-signed request remain transitively committed by `request_digest`; no unsigned wrapper field can broaden the decision. The browser may offer the broker-pinned eligible credential set; the returned credential ID is not precommitted in the challenge and must match that locally pinned set. User verification is required for every approval. The service serializes decision acceptance and credential revocation per credential, then signs a decision-acceptance proof containing the exact decision digest, credential, ordering position, and applicable revocation cutoff.
9. The broker retrieves the decision and verifies the WebAuthn assertion, exact challenge formula, RP ID hash, expected origin, user-presence/user-verification flags, returned pinned credential, every decision binding, current request state, current approver generation, and service-signed acceptance proof. Counter values are recorded as authenticator-specific risk signals, not treated as universal clone proof because synced credentials may report zero or non-monotonic counters. It rejects replayed, expired, malformed, mismatched, post-cutoff, or old-generation decisions. A pre-cutoff acceptance proof establishes only that the hosted service accepted the exact decision while that credential generation was current; it never carries the request or approval across a later broker credential-set change. Denial terminates safely.
10. The broker acquires the package-manager locks only for revalidation and execution, never across human approval. It verifies cached artifact and metadata hashes, approver generation, policy digest/current policy, and the package-manager pre-state. It reruns the simulation with network acquisition disabled and requires semantic equality with the approved package/version/action graph, including dependency and `Pre-Depends` edges. Approval does not bind internal unpack/configure ordering or trigger scheduling because APT does not expose a reliably enforceable complete effects trace.
11. Cached corruption, a current policy that rejects or further constrains the approved set, package-state drift, pending `dpkg` recovery, or simulation inequality moves the request to `stale`; the broker never silently re-resolves. If newer policy still authorizes the unchanged approved set, the broker records both policy digests and may proceed. Repository publication after the authenticated snapshot does not by itself invalidate intact cached artifacts.
12. The package helper installs only the cached, exact artifacts with the recorded root-owned APT configuration. It cannot guarantee identical maintainer-script effects, so it captures resulting package state and bounded normalized output without returning secrets or unrestricted privileged output to the agent.
13. The broker records and signs a terminal-event receipt containing the request digest, optional decision digest, terminal state, policy and approver generations, timing, and execution fields only when execution occurred.
14. The agent receives a bounded structured result. The website can display the broker-signed receipt; a root-controlled local verification command may independently verify the signed receipt for audit or recovery, but it is not part of routine approval.

### Package-manager pre-state

The engineering specification must give byte-level or semantic comparison rules for at least:

- installed, unpacked, half-configured, and trigger-pending package states;
- installed versions and architectures for every package participating in the plan;
- package holds, pins, foreign architectures, repository source definitions, trusted keyrings, and APT configuration used by the broker;
- interrupted `dpkg` state, pending triggers, conffile policy, configured APT hooks, and the broker's fixed environment;
- free-space minimums and artifact-cache availability.

Any state not explicitly classified as safe to ignore makes the request stale. The broker may accept a newer root-owned policy only if re-evaluation still authorizes the exact approved plan; a policy change can never broaden an existing approval.

## Durable State Machine and Recovery

The root broker persists every transition atomically. The normative terminal-state wire enum is `no_change | denied | expired | cancelled | invalid | stale | succeeded | failed | recovery_required`. User-facing text may differ, but receipts and APIs use only these spellings. The main legal paths are:

- `planning → pending → approved → executing → succeeded | failed | recovery_required`
- `planning → no_change`
- `planning | pending | approved → stale | expired | cancelled`
- `pending → denied`
- after the broker has persisted a canonical signed request envelope with both request ID and digest, later validation failure terminates as `invalid` and receives a normal terminal receipt; failures before a signed digest exists follow the intake-error contract below.

Additional invariants:

- `approved` means a valid decision has been consumed once; it is not permission to execute repeatedly.
- The broker atomically verifies and consumes the passkey approval while moving `pending → approved`. A denial moves `pending → denied`. The MVP has no local-confirmation substate or assurance escalation transition.
- Expiry, authorized local request cancellation, policy/pre-state staleness, failed final revalidation, or any broker-applied credential-set change invalidates any unconsumed decision. A broker credential-generation change also moves every non-executing old-generation request in `planning`, `pending`, or `approved` to terminal `stale`, even when the hosted service accepted its decision before a revocation cutoff. If final revalidation fails after approval, the request terminates as `stale` or `failed` as applicable; retry requires a new request and new approval.
- The protected local API provides bounded `request.list` and `request.get` views. For non-root callers, the broker applies `requester_uid = kernel_peer_euid` before lookup, ordering, cursor construction, or counting; UID 0 may inspect all requests and may optionally filter by requester UID. A list item contains only request ID, lifecycle state, creation and broker-authoritative expiry data, a safe typed-operation summary, and whether a terminal receipt is available. `request.get` returns the corresponding retained request view and terminal receipt when present. Results use a fixed maximum page size, deterministic ordering, and an opaque cursor cryptographically bound to the caller scope and filters; malformed, expired, or cross-scope cursors fail closed. Direct lookup of another UID's or a nonexistent request returns the same bounded `not_found_or_not_authorized` result. PID, executable, cgroup, agent labels, possession of an operation key, and knowledge of a request ID never expand read authority.
- A local cancellation call carries only the request identifier over the protected Unix socket. The broker obtains the current peer's effective UID from kernel-provided socket credentials and authorizes the transition only when that UID is 0 or exactly equals the request's persisted `requester_uid`. A new PID, changed executable, restarted process, or different cgroup/systemd unit under the same UID remains the same cancellation principal. Knowing a request ID, sharing the request group, matching an agent-supplied label, or reusing another UID's idempotency key never grants cancellation authority. Unauthorized and nonexistent targets return the same bounded `not_found_or_not_authorized` result to prevent request enumeration, while the broker records the true cause and peer metadata in its root-owned audit log.
- Cancellation is one atomic state transition. If cancellation wins while the request is `planning`, `pending`, or `approved`, the broker persists `cancelled`, invalidates any unconsumed approval, emits the signed lifecycle event and terminal receipt, and makes the device available for a fresh request. If `approved → executing` wins first, cancellation returns non-retryable `cancellation_too_late`; it never signals the helper or interrupts package-manager execution. Repeated cancellation by the authorized requester or root is idempotent and returns the existing `cancelled` result.
- The broker writes an execution-intent record and fsyncs it before invoking the package helper.
- Submission idempotency and execution idempotency are separate. Before planning, the broker durably claims the caller-generated `operation_key` within the authenticated effective-UID scope and binds it to a canonical fingerprint of the typed intake. The record points to the intake ID and, once created, the request ID/digest and eventual terminal receipt. An identical retry from any process under that UID returns the existing object and current state even while the device has an active package lifecycle; it is resolved before the new-request `busy` gate. A different canonical intake under the same key returns non-retryable `idempotency_conflict`. Crash recovery must resume or expose the claimed intake rather than silently creating a second request.
- The operation key is an opaque, bounded, high-entropy value generated and retained by the caller for the logical submission. Its exact encoding, minimum entropy, canonical intake fields, and retention window are normative local-API parameters; the broker retains the mapping for at least the corresponding request and receipt retention window. The key is not approval authority and is never sufficient to retrieve another effective UID's request.
- A separate per-request, one-use execution-attempt record plus the package-manager lock prevents concurrent or repeated privileged execution after approval.
- On startup, any request found in `executing` is reconciled against `dpkg` state and the helper journal. It becomes `succeeded`, `failed`, or `recovery_required`; it is never automatically executed again.
- `recovery_required` blocks new package operations until a root administrator repairs or explicitly acknowledges package-manager state.
- `approval_locked` is a retained device state, not a request result and not an unenrollment. It blocks planning and approval because the broker has zero active approval credentials, but it does not erase device identity, hosted binding, signed history, or receipt-verification keys. Root-controlled credential recovery through console or trusted SSH proposes a new non-empty set under the normal enrollment transcript and returns the device to `active` only after the new credential proves possession and the broker commits the update.
- Expiry authority is the broker's monotonic deadline bound to a boot identifier. The default request lifetime is 10 minutes; root-owned policy may choose a shorter lifetime but the broker rejects any configuration or request above the 30-minute hard maximum. The authoritative timer starts only when planning succeeds and the broker atomically signs and persists the `pending` request. Approval, retry, duplicate delivery, hosted resynchronization, or a transition to `approved` never restarts or extends it. Every `planning`, `pending`, or `approved` request expires conservatively on broker/host restart, boot-ID change, or suspend/resume when reliable monotonic elapsed-time accounting cannot be established; no approval survives reboot in the first slice. The hosted service and browser derive an approximate countdown from the broker-signed informational wall-clock timestamps. Only a fresh broker-signed status could attest remaining monotonic lifetime. Clock skew never extends the broker deadline, and the broker rejects a decision received after its monotonic expiry even if the website still shows time remaining.
- Broker signing-key loss, corruption, or intentional rotation requires a local root-controlled reset. The broker invalidates pending requests, archives the old public key for historical receipt verification, generates a new identity, and requires fresh trusted enrollment. The control plane cannot authorize this recovery.

### Intake-error contract

Before a canonical broker-signed request digest exists, `rootpermit` receives a bounded structured `intake_error` rather than a request receipt. The stable error enum is `invalid_input | policy_denied | busy | idempotency_conflict | rate_limited | planning_failed | repository_unavailable | resource_limit | timeout | credential_recovery_required | broker_recovery_required`. Every result includes an intake ID, retryable boolean, safe bounded message, and optional retry-after duration. `idempotency_conflict` is always non-retryable for that key; the caller must correct its retry bookkeeping or use a new key for a genuinely new logical submission. A new logical submission while the device is `approval_locked` returns retryable `credential_recovery_required` with no time-based retry hint and a safe indication that root-controlled credential recovery is required. After recovery, the caller must submit a new logical attempt with a new operation key; an identical retry still returns the original stable intake result. Idempotent recovery of an intake or request created before the lock is resolved before this gate and returns that original object's state or receipt. A terminal intake error is itself the stable result returned by an identical retry of its operation key. The broker records a signed local audit event that explicitly omits `request_digest`; unauthenticated garbage is represented only by rate-limited counters.

## Revocation

- The broker owns a monotonically increasing root-owned approver generation. Every request and decision binds to it.
- The broker stores a bounded set of at most five active approval credentials. Approval by any one member is sufficient, but the returned WebAuthn credential ID must identify a currently pinned member of the request's applicable generation. Adding, replacing, removing, or acknowledging revocation of a credential advances broker-owned credential state atomically; no operation may transiently expose more than five active credentials or silently select a replacement.
- Account authentication is not approval authority, but an authenticated or recovered account may initiate the authority-reducing act of revoking an approval credential. It cannot enroll, restore, replace, or reactivate one.
- The hosted service immediately quarantines a remotely revoked credential, stops accepting new decisions from it, and serializes a signed revocation cutoff with decision acceptance for that credential. The UI says `revocation requested` until the broker acknowledges the event.
- The broker processes the signed revocation event, atomically advances its approver generation, marks the credential revoked, and moves every non-executing request bound to an older generation from `planning`, `pending`, or `approved` to terminal `stale`. It publishes the revocation acknowledgement plus signed lifecycle events and receipts for those invalidated requests. A disconnected broker may acknowledge later; the service-side quarantine still prevents new hosted decision acceptance in the meantime.
- If that transaction revokes the final active credential, the broker also moves the enrolled device to `approval_locked`. The revocation is never refused and the device is never automatically unenrolled. New package planning and approval remain unavailable until a root-controlled console or trusted SSH recovery pins at least one replacement credential; the hosted account may initiate revocation but cannot perform this authority-adding recovery.
- A service-signed pre-cutoff acceptance proof prevents the hosted service from falsely classifying a post-revocation decision as earlier, but it does not grandfather a request across a broker-applied generation change. An approval page opened before revocation but submitted after the cutoff is rejected; a decision accepted before the cutoff may proceed only while its generation remains current and the request wins `approved → executing` before the broker advances that generation.
- Credential addition, replacement, removal, or acknowledged revocation never migrates an old request or decision into the new generation. The agent must submit a fresh request after every non-executing old-generation request becomes `stale`.
- Revocation cannot stop or undo a package transaction after execution begins.
- Hosted quarantine, account deletion, notification disablement, or hosted-history deletion never unenrolls the local broker. Root-controlled unenrollment is accepted only when no request is `executing` and no unresolved `recovery_required` evidence exists; it then invalidates non-executing requests, revokes current approval authority, emits the final signed binding event, and moves the broker to `unpaired` without deleting retained local audit evidence or historical receipt-verification keys.

## Authoritative Lifecycle and Hosted Projection

- The broker is the sole authority for request lifecycle and execution state. The hosted service never originates `approved`, `denied`, `expired`, `stale`, `executing`, or terminal execution outcomes.
- Every broker transition emits a signed append-only lifecycle event containing the request ID and digest, per-request sequence number, previous-event hash, broker epoch, transition, and protocol version. Terminal events carry the receipt fields required elsewhere in this document.
- The hosted service stores immutable events and derives a UI projection. Duplicates are idempotent. An out-of-order future event cannot advance the projection; a sequence gap freezes it at the last verified state and triggers broker resynchronization.
- Until a broker event confirms a submitted decision, the website says `decision submitted`, not `approved`. The UI always displays the last broker-confirmed state and its synchronization time.
- Hosted account and revocation records may show service-owned facts such as `credential quarantined` or `revocation requested`, but these must not be presented as broker lifecycle outcomes.

## Hosted Confidentiality Boundary

The MVP uses trusted-service confidentiality rather than claiming end-to-end secrecy from the official operator. The service may process minimized device, package-plan, decision, lifecycle, and bounded execution metadata so the web application can render and coordinate approvals. TLS, encryption at rest, strict tenant isolation, audited operator access, output sanitization, short retention, deletion controls, and an explicit privacy policy are required. The service never receives root credentials, broker private keys, approval private keys, or direct execution authority.

## Hosted Service Obligations

Hosted-only and free-of-cost are product commitments, not implementation details. Before public release, the official service must define:

- an immutable, server-derived `tenant_id` on every account-owned device, credential binding, request, decision, receipt, notification, object-store key, async job, websocket/subscription, audit event, and backup index; every read and transition authorizes the authenticated subject against both `tenant_id` and object relationship, never a request/device identifier alone;
- high-entropy non-sequential public identifiers, tenant-scoped storage/cache keys, row-level and application-layer checks, tenant-context propagation into workers and notifications, and tests covering APIs, queues, websockets, logs, object storage, support/admin tooling, exports, backups, and restores;
- phishing-resistant administrator access, protected deployments, dependency and secret scanning, audit logs, rollback, and separation between production operators and approval data;
- request-envelope and metadata retention periods, user-visible deletion behavior, backup scope, restore testing, and a privacy policy that states exactly what the service can see;
- per-account, per-device, per-IP, and global quotas to contain spam, notification abuse, storage exhaustion, and denial-of-wallet attacks against the free service;
- service availability behavior: local operations fail closed during an outage, pending requests remain authoritative at the broker, and no hosted recovery bypasses local policy;
- tenant-isolation tests and an incident-response path for a fleet-wide web-deployment or credential-verification compromise;
- a sustainability policy for operating costs and a continuity statement explaining what happens if the free service is discontinued.

Publishing the source does not prove that production runs those exact bytes. The project should publish build/deployment provenance where practical, but the MVP still asks users to trust the operator and official domain.

If the official free service is discontinued, installed brokers fail closed and lose remote approval functionality. The project may provide notice and a metadata/receipt export, but the MVP promises no compatible successor, self-host migration, or continued service. Users retain local receipts and can uninstall the broker; community forks remain possible under the source license but unsupported.

## Abuse and Resource Limits

- Per-effective-UID request-rate limits. The MVP has no broker-managed wait queue for package requests.
- Local list/read calls have per-effective-UID rate limits, a fixed maximum page size, bounded response bytes, opaque scope-bound cursors, and the retention rules below. Filtering occurs before counts and pagination so response shape, cursor behavior, timing targets, and error text do not become cross-UID enumeration channels.
- Idempotency lookup occurs before new-request rate, concurrency, and planning checks, but only within the authenticated effective-UID scope. Identical retries do not create new plans, notifications, quota consumption, or audit objects; conflicting reuse is bounded and rate-limited so guessed keys cannot become an enumeration oracle.
- Per-request and per-device download, disk, package-count, and transaction-size ceilings.
- One non-terminal package-operation lifecycle per device for the first slice, from `planning` until a terminal state. A later request receives the retryable `busy` intake error immediately and is neither queued nor planned; its eventual retry creates a fresh plan from then-current package state.
- Root-owned artifact-cache quotas and garbage collection for terminal or expired plans.
- Planning timeouts and circuit breakers for repository failures.
- Notification grouping and cooldowns so an agent cannot create approval fatigue.

## Retention, Export, and Purge

- The broker retains terminal requests, broker-signed receipts, local audit events needed to verify them, and submission-idempotency mappings for 90 days by default. Root-owned local policy may choose a different duration. A shorter duration must be disclosed to local callers; a longer duration remains subject to an explicit byte quota and documented capacity behavior.
- Active `planning`, `pending`, `approved`, or `executing` records and unresolved `recovery_required` records are exempt from age-based deletion. Their artifacts, journals, approval evidence, and recovery evidence remain until the lifecycle reaches a safe terminal state or root explicitly completes the documented recovery/purge procedure.
- The hosted service retains request envelopes, decisions, lifecycle projections, bounded execution metadata, and hosted receipt copies for 30 days after terminal completion by default. An authenticated account may delete its hosted terminal history earlier. Hosted deletion cannot delete, mutate, or invalidate the broker's local authoritative record and is not a credential-revocation or request-cancellation mechanism.
- Both tiers enforce byte and object-count quotas. Age-based cleanup removes eligible terminal records oldest-first. Quota pressure may reject new submissions or reduce optional cached artifacts, but it must never silently delete active authorization state, unresolved recovery evidence, the only local terminal receipt inside its configured retention period, or an idempotency mapping while its corresponding retained result is still discoverable.
- Local root may export retained requests, signed receipts, audit chains, and verification keys in a documented integrity-preserving format before purge. The hosted account may export its retained hosted history. Exports are snapshots, not authority, and importing them cannot recreate a pending request, approval, credential, or executable state.
- Local purge requires root authority and produces a signed local purge audit event containing bounded record identifiers and retention-policy context; it cannot purge active or unresolved recovery records through the ordinary command. Hosted early deletion is auditable and the UI reports `deletion_requested`, `deleted`, or a bounded failure state rather than claiming immediate physical erasure from backups.
- Backups follow the same classification. Hosted backups expire deleted or aged-out metadata within a documented maximum backup window; local backup and restore behavior is controlled by root policy. Restoring either tier cannot resurrect authorization: hosted projections must resynchronize from broker-signed lifecycle events, while restored local terminal data remains non-executable.

## Failure Behavior

- Control plane unavailable: request remains pending locally; nothing executes.
- Notification lost: the website can discover the pending request after sign-in; nothing executes automatically.
- Network or cross-tenant substitution alters a broker request or WebAuthn assertion: verification fails.
- A compromised trusted approval deployment misrepresents the transaction: the MVP cannot detect this. This is an explicit trusted-component failure outside the MVP's protection claims; operators must revoke affected credentials and requests through supported controls once detected.
- Control plane replays a prior approval: broker rejects the consumed request ID/digest.
- Broker or approver key mismatch: fail closed and require explicit recovery.
- Cached artifact or metadata corruption: hash verification fails and the request becomes stale. New repository publication alone is irrelevant after the authenticated snapshot is frozen.
- Approval website is unreachable or the passkey is unavailable: no approval; the authenticated requester or root may still cancel locally.
- Requester restarts or loses the request ID: any later process under the same effective UID can list its retained requests, inspect state and expiry, recover the terminal receipt, or select an eligible request for cancellation. It cannot discover another UID's request; root remains the only all-request recovery path.
- User denies or request expires: agent receives a stable structured denial/expiry result.
- Installation partially fails or the host crashes: durable reconciliation produces `failed` or `recovery_required`, records partial state, and never claims atomic rollback.
- Receipt upload fails: local signed receipt remains authoritative and sync retries later.
- Approver is revoked: the service rejects decisions accepted after the serialized cutoff. Until the broker receives the signed revocation, a pre-cutoff decision remains eligible only under the still-current generation and normal request checks. When the broker applies the revocation and advances the generation, every non-executing old-generation request becomes terminal `stale`; an already executing package transaction continues.

### Approved post-MVP direction: guaranteed remote cancellation

An authenticated account may eventually request cancellation of one exact `planning`, `pending`, or `approved` request. To make that cancellation reliable rather than best-effort, the broker must obtain a fresh, nonce-bound, service-signed status proof for the exact request immediately before `approved → executing`. A recorded cancellation causes the broker to transition the request to `cancelled` and publish its normal signed lifecycle event. If the status proof is unavailable, execution waits or the request expires; the broker never bypasses the check. Cancellation cannot interrupt a request after the broker has atomically entered `executing`.

This is not an MVP requirement. The first vertical slice relies on requester-or-root local cancellation, broker-enforced expiry, denial, policy/pre-state invalidation, and prospective credential revocation. The normative protocol must reserve compatible request-status and cancellation message types without requiring the hosted pre-execution check until the post-MVP feature is enabled by root-owned broker policy.

## Security and Product Acceptance Tests

The vertical slice is complete only when all of the following pass:

1. An unprivileged agent installs `ffmpeg` on a pinned Ubuntu Server 26.04 LTS AMD64 image after phone approval and never receives a shell or reusable credential.
2. The identical protocol and source architecture pass on the pinned Raspberry Pi OS Lite 64-bit Debian 13 image specified above.
3. The approval website shows exact package versions, dependencies, origins, download size, disk impact, device identity, expiry, and `Removals: none` before confirmation. A plan containing removals is rejected into a non-approvable view.
4. Agent, network, notification, cross-tenant, and unsigned-message substitution tests cannot produce an accepted approval. A malicious official web-deployment test is documented as a trusted-component failure outside the MVP's protection claims.
5. The broker rejects any assertion whose canonical decision does not bind to the exact locally created request digest, request ID, device, lifetime, approver generation, decision bit, and protocol version.
6. Request, digest, device, approver, expiry, protocol-version, or decision-bit substitution fails closed.
7. Replays, duplicate delivery, delayed approval after expiry, post-cutoff revoked-credential approval, every old-generation approval after the broker advances credential state, and approval after local cancellation fail closed. A pre-cutoff decision-acceptance proof cannot migrate or preserve a non-executing request across a credential-generation change. Any process whose kernel-reported effective UID equals the persisted `requester_uid`, plus UID 0, can cancel during `planning`, `pending`, or `approved`; a different UID, a forged requester label, or a caller holding only the request ID/idempotency key cannot. Restarting the requester under the same UID still permits cancellation, while changing only PID, executable, or cgroup never changes the authorization result. Cancellation racing `approved → executing` has exactly one durable winner, and cancellation after `executing` returns `cancellation_too_late` without interrupting the helper.
8. Package artifact replacement, metadata/cache corruption, symlink/path manipulation, relevant installed-state drift, policy rejection, and approved action-graph inequality are detected before execution.
9. Agent descriptions and notification text cannot influence authoritative approval fields.
10. Every authenticated request that receives a broker request ID and digest produces one receipt using the normative terminal-state enum: `no_change`, `denied`, `expired`, `cancelled`, `invalid`, `stale`, `succeeded`, `failed`, or `recovery_required`. Pre-authentication garbage is captured only in bounded counters and rate-limited audit events because it has no valid request digest.
11. WebAuthn verification requires the expected RP ID and origin, the exact domain-separated canonical-decision challenge, user verification, a locally pinned credential, replay protection, and an explicit authenticator-specific policy for counter anomalies. The MVP permits both device-bound and backup-eligible/synced passkeys but displays the credential class during local enrollment and never treats counter behavior as a universal clone detector.
12. Linux packages are signed, checksummed, and published with pinned signer fingerprints. The hosted service publishes source, dependency lockfiles, deployment-change records, and build provenance where practical. SBOMs and broader provenance are public-release gates, not proof-of-concept blockers.
13. The hosted implementation satisfies the defined tenant-isolation invariants under API, property/model, worker, websocket, storage-policy, notification, logging, backup/restore, and infrastructure-policy tests; no known path lets one account enumerate, read, approve, deny, revoke, or receive notifications for another tenant's objects.
14. A fresh user can complete account setup, Ubuntu enrollment through a trusted SSH root-administration session, first phone-only approval, receipt inspection, local revocation, and uninstall using only the README. Physical access is never required; after enrollment, routine approval never requires any machine session.
15. The broker applies a 10-minute default and rejects any effective lifetime above 30 minutes; root-owned policy can shorten the lifetime. Approval just before expiry, duplicate delivery, retry, and hosted resynchronization do not extend the original broker-monotonic deadline.
16. While one package-operation lifecycle is non-terminal, every later `package.install` intake receives `busy`, `retryable: true`, and a bounded `retry_after`; it creates no plan, approval notification, or queue entry. After the first lifecycle terminates, retrying plans from the new package pre-state rather than reusing any earlier simulation.
17. If the client loses the first submission response, retrying the identical canonical intake with the same `operation_key` returns the original intake result, request/current state, or terminal receipt across connection loss and broker restart; it creates no second request or notification and is not rejected as `busy`. Reusing that key with any changed canonical intake returns non-retryable `idempotency_conflict`. A new key is treated as a new request and receives normal concurrency handling.
18. After a requester restart and loss of its request ID, a process under the same effective UID can page through only that UID's retained requests, read safe request state/expiry/summary data and any terminal receipt, and cancel an eligible recovered request. UID 0 can inspect all retained requests. A different UID, forged UID/filter field, known request ID, known operation key, malformed or replayed cursor, changed PID/executable/cgroup, and page-boundary race cannot reveal whether another UID's request exists; direct lookup returns `not_found_or_not_authorized`, list counts and cursors remain scoped, and pagination is bounded and deterministic.
19. Terminal local requests, signed receipts, required audit evidence, and their idempotency mappings remain discoverable for the 90-day default; hosted terminal metadata ages out after the 30-day default and authenticated early deletion affects only the hosted copy. Age cleanup, quota pressure, backup expiry, export, local root purge, hosted early deletion, and restore tests cannot delete a non-terminal lifecycle, discard unresolved `recovery_required` evidence, break a retained receipt's verification chain, resurrect execution authority, or expose another tenant/UID's records.
20. Enrollment succeeds from a correctly authenticated and host-verified SSH administrative session with root authority and otherwise uses the same transcript and state machine as console enrollment. A browser-only attempt, hosted-account takeover, replayed pairing payload, unprivileged local process, agent-controlled terminal output, lost SSH session before broker-side confirmation, or confirmation from a different enrollment attempt cannot move the device from `provisional` to `active`; failed and abandoned nonces remain single-use.
21. An `active` device can pin one through five distinct approval credentials and accept a valid, user-verified assertion from any one currently pinned credential without requiring a quorum. Each credential can be revoked independently without removing the others. A sixth active credential, duplicate credential ID, empty proposed enrollment/recovery set, assertion from an account credential not pinned by the broker, concurrent additions that would cross the cap, or hosted-only add/replace attempt fails closed with a named error and cannot mutate the active set. Root-controlled addition or replacement through console or trusted SSH atomically advances the credential set and generation; it never implicitly evicts an existing credential or grants authority through hosted account recovery. Zero active credentials can result only from authority-reducing revocation and must place the device in `approval_locked` as tested below.
22. After every previously pinned credential is lost or unavailable, an administrator in an authenticated root-controlled console or trusted SSH session can replace the credential set without presenting an old passkey. The new credential must produce a user-verified assertion over the exact service-signed enrollment statement, and the broker must verify the originating root-confirmed transcript before advancing the credential generation. A hosted-account session, pairing payload, proposed-new-credential assertion without root confirmation, unprivileged local process, or stale transcript cannot add authority; pending requests under the prior generation fail closed.
23. Adding, replacing, removing, or acknowledging revocation of any approval credential atomically advances the broker generation and makes every `planning`, `pending`, or `approved` request from the prior generation terminal `stale`, including a request with a valid pre-cutoff decision-acceptance proof. Each invalidated request emits exactly one signed lifecycle event and receipt, releases the device's active-lifecycle slot, and cannot be resumed or migrated; retry requires a new operation key, plan, request digest, and approval under the new generation. If credential rotation races `approved → executing`, exactly one durable transition wins: rotation first yields `stale`, while execution first continues once under the original generation and is not interrupted.
24. Revoking the final active credential succeeds from both the root-controlled local path and the authenticated-account remote-revocation path, advances the generation, makes every non-executing old-generation request terminal `stale`, and leaves an already executing transaction untouched. The device enters `approval_locked`, retains the same broker/device identity and verifiable history, and returns `credential_recovery_required` for each genuinely new package submission without creating a request or notification. It cannot accept an approval, silently retain the revoked credential, or become unenrolled. Idempotent lookup of an older intake/request still returns its original state. Root-controlled recovery through console or trusted SSH can pin a new non-empty set without an old credential and return the device to `active`; hosted-account access, a proposed credential alone, agent output, or browser-only action cannot unlock it. Failed or interrupted recovery remains `approval_locked`, and no stale request or prior intake is resurrected.
25. Unenrollment succeeds only after explicit confirmation in an authenticated root-controlled console or trusted SSH session. Hosted account takeover, account deletion, device quarantine, notification disablement, hosted-history deletion, browser-only action, pairing-payload possession, and unprivileged local calls cannot make the broker discard or replace its binding. A successful unenrollment makes each `planning`, `pending`, or `approved` request terminal `stale`, revokes the pinned credential set, emits one final signed binding acknowledgement, retains historical keys and receipts for verification, and leaves the broker `unpaired`; reconnection requires a complete fresh enrollment. If `executing` or unresolved `recovery_required` state exists, unenrollment fails closed without changing the device or request state and succeeds only after execution reaches a terminal result or root resolves the recovery condition.
